# ADR-0001: Модель повышения привилегий (elevation)

Статус: принято. Контекст: Control 1.0.1 требует администратора на всё приложение
(`requireAdministrator`), R20 против целевого «повышение только для нужной операции».

## Решение

Основное приложение работает **без прав администратора**. Операции, которым нужны админ-права
(создание/удаление службы `zapret`, копирование `WinDivert.sys` в `System32\drivers`,
`sc`/`net stop` для системных служб), выполняются через **elevated helper**:

- Rust формирует самоописанный сценарий операции (список шагов с аргументами) во временный
  JSON-файл в `%APPDATA%\control\pending-elevation\`.
- Запуск: `Start-Process -Verb RunAs` небольшого встроенного хелпера
  (`control-elevate.exe`, bundled с приложением, помечен `requireAdministrator` в своём манифесте),
  который читает файл плана, выполняет шаги, пишет JSON-отчёт (exit code каждого шага) в temp
  и завершается. Приложение читает отчёт и мапит результат в операцию.
- UAC-отмена пользователя → понятная ошибка `UAC_CANCELLED`, отличимая от ошибки сценария
  (лечит R13: отчёт и коды вместо «no throw ⇒ успех»).
- Файл плана валидируется хелпером по фиксированному набору разрешённых действий
  (whitelist), путь отчёта передаётся явно.

## Альтернативы

- Требовать админ на всё приложение — отвергнуто: против ТЗ, избыточная атака-поверхность.
- PowerShell -Verb RunAs с длинным inline-скриптом — отвергнуто: нечитаемо, нет отчёта,
  экранирование ломается.

## Последствия

- Нужен второй маленький binary в пакете (cargo workspace bin), манифест requireAdministrator.
- Написание службы/драйвера теперь явно показывает, что именно будет выполнено — план можно
  показать в UI перед подтверждением.
- Хелпер собирается в том же пакете отдельным бинарём и поставляется как sidecar
  (`externalBin` в `tauri.conf.json`).
